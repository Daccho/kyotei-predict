# kyotei-predict

競艇（ボートレース）の公開データから、レース結果の**較正された確率分布**を推定し、
オッズが示す市場確率より高い目だけを買うパイプライン。

**成功指標は的中率ではなく回収率。** 舟券の払戻率は 75%（控除率 25%）なので、
「1号艇が1着」と常に答えれば的中率 55% は出るが回収率は 50% 台にしかならない。
解くべき問題は当てることではなく、**較正された確率を出して期待値がプラスの目だけ買うこと**。

仕様は [SPEC.md](SPEC.md)。

## 現状

| Phase | 内容 | 状態 |
|---|---|---|
| 1 | 取得・パース・格納 | 実装済み・検証済み |
| 2 | リーク防止特徴量 | 実装済み・リーク検証テスト通過 |
| 3 | 1号艇1着の二値ベースライン | 実装済み |
| 4 | 6艇 conditional softmax → 3連単120通り | 実装済み・合計1.0検証済み |
| 5 | 回収率バックテスト | 実装済み |
| 6 | 日次推論レポート | 実装済み |

全 382 テスト通過。

## セットアップ

```bash
uv sync                      # Python 3.12 + polars / LightGBM / lhafile
./scripts/setup_db.sh        # PostgreSQL を使う場合のみ（parquet だけでも動く）
uv run pytest tests/ -q
```

LZH の解凍は pure-Python の `lhafile` を使うので `lhasa` の導入は不要。

## 使い方

```bash
# 1. 取得（冪等・全体1req/s上限。中断しても再実行で続きから）
uv run python -m kyotei.download --start 2015-01-01 --end 2026-12-31 --kind both --fan

# 2. パース → parquet（年ごとのパース成功率を出す）
uv run python -m kyotei.export

# 3. 特徴量（リーク防止）
uv run python -m kyotei.features        # DB経由
#   parquet から直接 ft.build() でも同じ

# 4. 学習
uv run python -m kyotei.model --feature-set morning --lane1-baseline --walk-forward

# 5. バックテスト（閾値は必ず valid=2024 で決める）
uv run python -m kyotei.backtest --split valid --payouts data/parquet/payouts.parquet

# 6. 当日の買い目 → reports/YYYY-MM-DD.md
uv run python -m kyotei.predict --payouts data/parquet/payouts.parquet

# レースを指定する（場は場コードでも名前でも可）
uv run python -m kyotei.predict --stadium 大村 --race 4     # 大村4R のみ
uv run python -m kyotei.predict --stadium 24               # 大村の全レース
uv run python -m kyotei.predict --race 12                  # 全場の12R
uv run python -m kyotei.predict --date 2026-07-26 --stadium 住之江 --race 4
```

指定すると出力先も分かれる（`reports/2026-07-26-24-4R.md`）。
**絞り込みはスコアリングの後に行う**ので、同じ日の他レースが履歴として正しく効く。

Colab から回す場合は [`notebooks/colab_pipeline.ipynb`](notebooks/colab_pipeline.ipynb)。
**Notebook はドライバであって成果物ではない**（SPEC §5）。ロジックは `src/kyotei/` にある。

> **GPU について**: SPEC は PyTorch/NN を禁じて LightGBM (GBDT) を指定している。
> GBDT は CPU 律速なので **GPU ランタイムを選んでも速くならない**。
> Colab の価値は GPU ではなく、Drive による永続化と大きめのメモリ。

## 設計上の重要な判断

### 1. B/K のレイアウト仕様は公開されていない

SPEC §3.2 が指す
[layout.html](https://www.boatrace.jp/owpc/pc/extra/data/layout.html) は
**「モーターボートファン手帳」= `fan{YYMM}` 専用**のレイアウト表で、
番組表(B)・競走成績(K)の記述は無い。`od2/{B,K}/dindex.html` も中身の無いフレームページ。

代わりに B/K は**自己記述形式**で、各レースブロックが自分の列ヘッダを持っている。
そこからバイト位置を転記し、**独立ソース間の一致**で裏を取った：

- B と K の両方が公開するモーター番号・ボート番号・登番が一致すること
- 3連単の払戻組番が 1〜3着の枠番と一致すること
- 1レース必ず6艇、レース内で進入コースが重複しないこと

検証は `tests/test_parse_pilot.py`。

### 2. バイト単位でスライスする

固定長レイアウトは**バイト**で数える。選手名・支部は全角で、CP932 では1文字2バイト。
先に文字列へデコードすると、最初の全角フィールド以降の全カラムが右にずれる。
`fixedwidth.py` は全てバイトオフセットで、デコードはフィールド単位で行う。

### 3. リーク防止は構造で保証する

過去成績は全て

```
prior_sum   = cum_sum().over(group) - current_value
prior_count = cum_count().over(group) - 1
```

で作る（発走時刻順にソート済み）。現在行が自分の集計から算術的に除かれ、
後の行はまだ累積和に入っていない。**未来を含みうる窓や結合が存在しない。**

縮小（shrinkage）の基準は全期間平均ではなく**expanding な全体平均**。
全期間平均はそれ自体が未来の関数なので使えない。

検証は SPEC §2.1 が要求する実験そのもの：
**未来のレースの着順を書き換えても、それ以前の特徴量が1バイトも変わらない**
（`tests/test_features.py::test_editing_the_future_does_not_change_the_past`）。

### 4. 進入コースは「賭けられない特徴量」

SPEC §2 A は実際の進入コースを支配的特徴量とする。**結果を説明する上ではその通り**だが、
締切時点では分かっていないので、それを食うモデルは実運用できない。
そこで特徴量セットを段階に分けた：

| セット | 内容 | 用途 |
|---|---|---|
| `morning` | 番組表のみ | **実際に賭けられる。** 日次推論はこれ |
| `prerace` | + 展示タイム・気象 | 直前情報が取れる場合 |
| `realised` | + 実際の進入コース | **診断用の上限値。** 賭けには使えない |

`morning` でも進入コースを完全に捨てるのではなく、
**その選手が普段どれだけ内側に進入するか**の履歴を持たせている
（`racer_goes_inside_rate` / `racer_course_gain_rate`）。

`predict.py` は `morning` 以外で学習されたモデルでの実行を**拒否する**。

### 5. レース内 softmax（120クラス分類にしない）

各艇を独立に sigmoid すると6艇の確率が1にならず期待値計算が破綻する。
1艇ごとにスコア s_i を出し、**レース単位で softmax** する：

```
P(i が1着) = exp(s_i) / Σ_j exp(s_j)
```

3連単120通りは Plackett-Luce（非復元抽出）で導出：

```
P(i→j→k) = P(i) × P(j)/(1-P(i)) × P(k)/(1-P(i)-P(j))
```

`tests/test_model.py` で「6艇の合計=1.0」「120通りの合計=1.0」
「lane i で始まる120通りの和 = P(i が1着)」を検証している。

### 6. オッズの限界（重要）

**K ファイルの払戻金は「当たった組番」の分だけ存在する。**

- **回収率は正しく計算できる**：戻ってくる金は当たった券の分だけなので、
  実払戻だけで足りる。バックテストは実データの払戻金で決済している。
- **締切前の期待値計算はできない**：買う候補すべての価格が必要になる。

そこで価格側はモデル化した。各組番の期待払戻を、
**その組番が過去に付けた配当の expanding 平均**とする（リークなし）。

```
EV = P_model(組番) × 期待払戻 / 100 ≥ 閾値
```

これは本物のオッズ板ではなく**その組番の基準率での近似**。したがって
「EV > 1」は「モデルが履歴より起こりやすいと考えている」という意味であり、
**生きた市場に勝ったという証拠より弱い**。実運用前に本物のオッズに差し替える必要がある。
この注意はレポートに毎回印字される。

### 7. 取得は「頻度」で制限する

計測すると、オリジンの TTFB は約10〜11秒（接続再利用でも改善しない）。
逐次1秒間隔だと全期間で約23.5時間かかる。

SPEC §3.1 の「全力で叩かない」はサーバへの負荷の話なので、
**トークンバケットで全体を1req/s以下に固定**し、その上限を埋めるだけのワーカー（12本）で
待ち時間を隠した。実測 0.93 req/s、所要 約2.4時間。
**ワーカー数はスループットのダイヤルではない**（`--rate` が上限）。

取得は年ごとに B と K を揃えて進むので、**完了した年はその時点で完全な年**になる。

## 端から端まで回した結果（2015–2016、スモーク）

`scripts/smoke_pipeline.py --start 2015-01-01 --end 2016-12-31`（時系列70/15/15分割）:

```
B/K パース成功率      : 100.000%（失敗0）
6艇揃ったレース       : 99.1%
リーク検証            : 27特徴量が未来改変で不変
レース内確率の合計    : min 1.000000  max 1.000000
Brier（較正前）       : 0.10592
Brier（較正後）       : 0.10342     ← 1/6ベースライン 0.13889
ROC-AUC               : 0.8329

EV閾値   購入率    回収率
1.00     16.1%     0.7474
1.10     14.1%     0.7515
1.20     12.3%     0.7449
1.30     10.8%     0.7417
```

**モデルは確率推定として機能している**（Brier がベースラインを明確に下回り、較正後の
リライアビリティのズレは低確率帯でほぼ0）。

**しかし回収率は約0.75で、これは払戻率75%とほぼ一致する。** つまり市場に対する優位は無い。
さらに決定的なのは、**EV閾値を上げても回収率が改善しない**（0.747→0.742）ことである。

理由は明確で、価格が「組番ごとの過去平均」という**レースによらない定数**だからである。
すると `EV = p × 定数` になり、EV フィルタは実質「モデル確率の高い組番を買う」だけに退化する。
**「このレースで市場が間違えている」を表現できない。**

したがって残っている本質的な課題はモデルではなく**データ取得**である：
締切前の**レース単位の実オッズ**が無ければ、期待値ベースの購入判断は原理的に成立しない。

なお公式サイトは
**「番組表閲覧」「オッズ情報・結果」を2025年3月5日でサービス終了**しており、
過去オッズは公式から取得できない（`download.html` に明記）。

## 実オッズと直前情報（重要な進展）

日次ファイル(B/K)には**オッズも直前情報も入っていない**が、サイト側にある。
`scrape.py` で取得・パースできることを確認した。

```
直前情報   /owpc/pc/race/beforeinfo?rno={R}&jcd={jcd}&hd={YYYYMMDD}
3連単オッズ /owpc/pc/race/odds3t?rno={R}&jcd={jcd}&hd={YYYYMMDD}
```

```bash
uv run python -m kyotei.scrape --date 2026-07-25 --stadium 大村 --race 4
```

```
直前情報
  気温 31.0℃  水温 33.0℃  風速 2.0m  波高 1.0cm  晴
  1号艇 展示 6.99  チルト -0.5  体重 56.9  展示進入 1  展示ST 0.27
  ...
3連単オッズ: 120/120 通り
  市場確率の合計: 1.0012
```

**パースの正しさは独立に裏取りできている**：各オッズの逆数を払戻率75%で割り戻した
「市場確率」の合計が **1.0012**。列がずれていたり2着と3着を取り違えていたら
この数字は1にならない。120通りの欠けも無い。

これが解くもの:

| 既知の制約 | 状態 |
|---|---|
| 実オッズが無い（EVフィルタが定数価格で退化） | **解ける。** 締切時オッズ120通りが取れる |
| 気温・水温が無い | **解ける。** 直前情報ページにある |
| 進入コースが締切前に不明 | **大幅に改善。** スタート展示の進入コースが取れる |

残る制約:

- **保存期間**。自前アーカイブで開催を確認した日で検証すると、2020-01-01 はオッズあり、
  **2015-01-01 と 2016-06-15 は「該当レース無し」**。つまり学習期間(2015–2023)全体の
  実オッズは取れない。valid/test 期間に絞るのが現実的。
- **取得コスト**。1レース1リクエストなので1日約150件（1req/s で数分）は容易だが、
  1年分の全レースは約53,000件＝約15時間。日次運用は安いが、過去の一括取得は高い。

## 未解決・既知の制約

1. **本物のオッズが無い**（上記6）。**最大の制約で、これが解けないと回収率は控除率に張り付く。**
   公式は2025年3月5日でオッズ提供を終了済みなので、別ソースが必要。
2. **気温・水温が日次ファイルに無い**。K の気象行は `晴 風 北 2m 波 1cm` で終わる。
   SPEC §2 C が挙げる水温・気温は別ソース（直前情報）が必要で、現在は NULL。
3. **B は選手名を4文字に略し、それは先頭一致ではない**
   （`マイケル田代` → `マイケ田`）。**名前で JOIN してはいけない**、登番で JOIN する。
   テストで固定済み。
4. **欠場艇の扱い**。`course` が NULL のエントリが存在する（2020-01-01 で1件）。
   現在は6艇揃って勝者が1人のレースだけを学習に使っている（`complete_races`）。
5. **同着（同着）がある**。1レースに勝ち組番が2つ出ることがあり、それぞれに払戻が付く。
   決済は (レース, 組番) で結合して各券に自分の配当を払う実装にしてある。
6. **1/4ケリーの資金は固定**（複利にしていない）。長期の資金曲線を見るなら要変更。
7. **複勝が1通りしか出ないレースが稀にある**（2020-01-03 は228レース中2件）。
   6艇完走していても生データが `複勝 4 380` の1行だけ、という状態。理由は不明で、
   パーサは原文を忠実に再現している。3連単しか決済に使っていないので影響は無い。
8. **回収率が100%を超えたらリークを疑う**。公開されている競艇AIは概ね80〜95%。
   バックテストは100%超で警告を出す。
